Gate: REVISE

- Correct: The plan's core answer to the user's question is right: the TUI can access most of the needed information after a data-layer widening. The schema already defines `active_step`, `blocked`, and `blocker_kind` (`stores/tasks/schema.yaml:70-94`), structured `plan_review_log` (`stores/tasks/schema.yaml:116-123`), structured `cycles` with `phase`, `cycle`, executor, and review gate (`stores/tasks/schema.yaml:124-146`), and `current_phase/current_cycle/plan_source` (`stores/tasks/schema.yaml:147-154`). The current TUI `TaskRow` has only flattened `plan_review_summaries` and `cycle_summaries` (`src/tui/data.rs:176-201`), and the load path currently parses those fields only into summary lists (`src/tui/data.rs:1327-1333`), so Phase 1 is a necessary and feasible first step.
- Correct: The guardrails in the plan are directionally sound: historical green/red should require structured `plan_review_log` or `cycles` proof (`docs/worklog/2026-05-13/07-watch-task-map-implementation-plan.md:213-217`), and projection tests before renderer snapshots (`...:218`) is the right order.

- Blocker: The plan does not anchor the implementation to the current focused TUI rendering path, so a worker could implement the map in the wrong place or add a parallel abstraction. The actual ratatui focused task view already groups rows via `task_watch_projection` (`src/tui/render.rs:884-918`) and formats task rows through `format_row_line_for_task_projection` / `format_task_line_with_status` (`src/tui/render.rs:1292-1403`). The existing semantic projection is in `src/tui/semantics.rs:59-92`. Revise Phase 2/3 to explicitly extend or wrap this existing projection/render path, not create an unrelated `TaskMapProjection` that the focused table never consumes. Also state that `src/cli/watch.rs` is legacy/ANSI and is not the target unless explicitly kept in parity.

- Blocker: The design target includes a `ready task awaiting coding` row (`T004`) with `● │ □ · ·` (`docs/.../07-watch-task-map-implementation-plan.md:19`), but the schema has a framework `ready → executing` on-entry transition (`stores/tasks/schema.yaml:250-252` covers code-review phase completion; `ready → executing` is in the surrounding lifecycle and current comments describe it as framework-fired). In current ADR/schema terms, a durable active coding wait is normally `lifecycle=active, active_step=coding`, not a stable `ready` visual state. Revise the examples and rules to map the execution slot from `active_step=coding/current_phase/current_cycle`, and treat legacy/status-only `ready` as a compatibility fallback or unknown/implied state.

- Blocker: Plan-review superscripts are underspecified. `plan_review_log` has no explicit `cycle` field (`stores/tasks/schema.yaml:116-123`); only its length and latest gate are available. The acceptance test says "plan review cycle 3 from structured log" (`docs/.../07-watch-task-map-implementation-plan.md:148`), but the persisted source is `plan_review_log.len()`/latest entry, not a cycle number. Revise the projection contract: planning-cell superscript should be derived from plan-review attempt count (probably `plan_review_entries.len()` when >1, or a precisely defined current-attempt count), with source/confidence recorded as `plan_review_log.length`, not `cycle`.

- Blocker: Code-phase cell derivation needs stricter grouping rules. `cycles[]` appends executor entries and later patches the matching `phase/current_cycle` review (`src/handlers/submit.rs` behavior; schema shape at `stores/tasks/schema.yaml:124-146`). For a phase with retries, the renderer must group by phase, choose the latest/max cycle for that phase, and then decide cell state from the latest review gate unless the phase is currently active. Previous phases should be green only when their latest review gate is `PASS`; a `REVISE` on the current phase should not accidentally render as a passed `▣`. Add these rules and tests for PASS after earlier REVISE, current executing cycle 2 after REVISE, current code_review cycle 2, and FAIL/blocked.

- Note: The plan overstates `transition_history` availability for precise blocked placement. `TaskRow.recent_events` exists, but `attach_recent_events` only loads the newest five events per display id (`src/tui/data.rs:1767-1779`), while `accepted_at` is the only special-purpose transition-history aggregate currently preloaded (`src/tui/data.rs:1257-1279`). If blocked placement inside a phase depends on an older `mark_drive_failed` event, the plan needs a dedicated query for the latest relevant failure/interruption event, or it must keep the existing guardrail: render `▲`/`△` outside the map with reason when placement is not provable.

- Note: Phase 1 structs should be typed/serde-backed, not just ad-hoc strings. At minimum derive `Deserialize`, tolerate `review: null`, missing optional timestamps/summaries, malformed JSON as empty/unknown, and store enums or normalized strings for gates. This is important because old cockpit test schemas degrade optional columns to `'[]'` (`src/tui/data.rs:1243-1245`) and many tests construct `TaskRow::default()` directly.

- Note: The visual table acceptance is not yet strong enough to guarantee the btop-like design. Current task lines are prose/status-first (`src/tui/render.rs:1392-1408`), and current focused rendering inserts group headers (`src/tui/render.rs:900-909`). If the desired result is literally `ID | SUMMARY | MAP | REASON | AGE | TIER`, revise Phase 3 to specify: header rendering in the focused task pane, whether projection group headers remain or are suppressed, fixed/right-aligned AGE/TIER widths, map width policy, title truncation after fixed columns, and ratatui `Span` style tests that strip ANSI/visible width correctly. Include a rendered-buffer snapshot for the exact sample shape.

- Note: The plan should include detail-pane work in a concrete phase. It requires the detail renderer to decode the selected map in text (`docs/.../07-watch-task-map-implementation-plan.md:186`), but current details use progress/presentation/debug fields rather than a map decoder (`src/tui/detail.rs` task path). Add a Phase 3 task to expose the projection explanation/source/confidence in detail.

- Note: Color implementation should be ratatui style roles, not string coloring. Phase 4 should define the mapping from `MapColor` to `ratatui::style::Color/Style` and test spans/styles in `src/tui/render.rs`, while keeping glyph-only meaning for monochrome. Do not delay all color verification if color is essential to "active / passed / failed / waiting" in the design.
