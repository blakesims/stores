stores watch truthfulness gap report

What stands between today’s cockpit and the ideal: each store declares its own primitives/lifecycles/statuses once, and stores watch honestly renders them without hand-written dictionaries, over-fitted translations, or per-store display code.

High
Frontend coupling

Top cards, sections, rows, and details each classify rows separately.

Medium
Schema ambiguity

Several stores expose more than one truth axis: legacy status, lifecycle tuples, waiting overlays, blocked flags.

Medium
Translation risk

Recent semantic mappings improved UX but can hide contradictions or invent vocabulary not present in the store contract.

1. The ideal target

Ideal: a store schema declares the operator-visible lifecycle and display primitives. The watch UI discovers those primitives and renders:

  • top-card slots from declared lifecycle groups,
  • focused table sections from the same lifecycle groups,
  • row state from the row’s declared lifecycle/status fields,
  • detail debug from raw fields, clearly separated.

No bespoke dictionary like blocked + blocker_kind=runner → runner-failed should live in frontend rendering unless that mapping is declared by the store itself.

4. Concrete current symptoms

Tasks: mismatched grammar

Top card: queued / working / gate / done / waiting / failed
Sections: QUEUED / ACTIVE / AWAITING HUMAN ACCEPTANCE / HELD-TRIAGE
Rows:     queued / plan / plan-gate / exec / accept / runner-failed

The pieces are locally useful but not one information schema.

Observations: recently improved but still translated

Schema: lifecycle + contract_state + waiting_kind + outcome
Top:    candidates / investigate / contract gate / waiting
Rows:   candidate / contract-approved / next:promote/resolve

Option A reduced double counting, but the rule lives in apply_obs_to_flow, not in the schema.

Adding a new store is not automatic

A new store currently needs schema plus loader, row enum variant, lane enum, top-card fold, section classifier, formatter, details, tests.

Frontend suppresses duplication manually

Example: hiding contract: in observation rows and suppressing raw task tuples are renderer decisions. Good UX, but not declarative.

6. Why per-store custom code is both good and bad

Good

  • Tasks, observations, intake, reviews, and engine really have different domain semantics.
  • Hand-written code can produce excellent UX quickly.
  • It can hide legacy implementation details while schema cleanup lags.

Bad

  • Every layer can invent vocabulary.
  • UI truth can drift from schema truth.
  • Adding a store is expensive and error-prone.
  • Fixes over-fit current fixture data rather than enforcing a durable primitive.

7. Proposed fixes

Fix A — Declarative watch projection in every store schema

Add a watch: block to each store schema. It declares the canonical operator projection, not just raw fields.

watch:
  lane_label: TASKS
  slots:
    - {id: queued,  glyph: "◌", attention: flow,  when: "lifecycle == 'queued' && !blocked"}
    - {id: working, glyph: "◆", attention: flow,  when: "lifecycle == 'active' && active_step in ['planning','coding']"}
    - {id: gate,    glyph: "◇", attention: flow,  when: "active_step in ['planning_review','coding_review','wrapping']"}
    - {id: done,    glyph: "✓", attention: exhaust, when: "lifecycle == 'done'"}
    - {id: waiting, glyph: "△", attention: flow,  when: "blocked && blocker_kind in ['capacity','dependency','human_acceptance']"}
    - {id: failed,  glyph: "▲", attention: fault, when: "blocked && blocker_kind in ['runner','test_failure','deploy']"}
  section_by: slot
  row:
    primary: stage_label
    suppress_if_same_as_section: true

Result: top card, sections, and row suppression all use the same declared slot. New stores become visible if they provide a watch projection.

Tradeoff: still allows declarative expressions. The schema becomes responsible for operator truth; validators must ensure rows match exactly one visible slot unless explicitly multi-axis.

Fix B — Normalize store lifecycle primitives first, then generate watch

Deeper approach: define a universal store primitive model and migrate schemas toward it.

Store row primitive:
  phase: front | work | gate | exit | wait | fault
  stage: store-specific value, e.g. plan-gate, contract-draft, tool-fault
  outcome: optional terminal reason
  attention: neutral | flow | exhaust | fault
  debug: raw implementation tuple

Then every store row literally carries its operator phase/stage. Watch does not translate; it groups and renders these fields.

Result: closest to the ideal: frontend becomes generic.

Tradeoff: larger schema migration and doctrine decision. Existing task/observation fields must be reconciled or made derived/generated.

8. Recommended path

Recommendation: do Fix A first as a schema-declared watch projection. It is the smallest step that stops the frontend from being the hidden domain model.

  1. Add watch projection metadata to tasks and observations only.
  2. Generate top-card counts and focused sections from that metadata.
  3. Make row renderers context-aware: if section is QUEUED, do not repeat queued in each row.
  4. After two stores prove the pattern, generalize to intake/reviews/engine.
  5. Then decide whether Fix B is worth migrating toward.
