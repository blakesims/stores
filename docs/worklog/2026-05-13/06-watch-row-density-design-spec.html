stores watch row density design spec

The top cards are getting close. The focused row list is still prose-heavy: age, tier, no-worktree, not scaffolded, workspace, runner failure, review reason, and summary are all competing in one free-form sentence. This spec sketches four approaches for turning that into a readable cockpit table inspired by btop's column discipline.

What btop is doing well

  • Column headings are explicit. The operator knows what each token under it means.
  • Columns have visual identity. Headings, numeric columns, and graph columns use different color/weight.
  • Rows are not sentences. Each cell has one job: pid, program, command, threads, user, memory, cpu.
  • Long fields get a budget. Command expands/truncates; fixed columns stay stable.
  • Sort direction is visible. Cpu% ↑ tells you the table's ordering.

Current problem in stores watch

▾ WORKING (2) T002 ◆ plan no worktree not scaffolded age:6h tier:T3 · workspace:none · synthetic active planning task T004 ▣ exec no worktree ▮ ··· age:6h tier:T3 · synthetic ready task awaiting coding ▾ FAILED (2) T010 ▲ runner-failed exit 42 age:6h tier:T3 · reason:{"exit_code":42,"kind":"runner_crash"} T005 ▲ review plan-reviewer marked NOT_READY: Synthetic plan rejected to create blocked state
Diagnosis: this is not a table yet. It is a row id + stage followed by a bag of facts. Some facts are state, some are actionability, some are debug, some are summary. Because they are not columnized, every row must be parsed from scratch.

Approach 1 — Fixed btop-style columns per focused store

Best first implementation Give each focused store a stable column table. Tasks get task-specific columns; observations get observation-specific columns. This is not fully generic, but it is highly readable.

TASKS sort: slot → age ID STAGE SIGNAL READY AGE TIER SUMMARY ▾ QUEUED (2) T001 ◌ no worktree not scaffold 6h T3 synthetic queued inactive plan task T006 ◌ no worktree not scaffold 6h T2 synthetic abandoned queued task ▾ WORKING (2) T002 ◆ plan no worktree not scaffold 6h T3 synthetic active planning task T004 ▣ exec phase 1/1 ready 6h T3 synthetic ready task awaiting coding ▾ FAILED (2) T010 ▲ runner exit 42 — 6h T3 synthetic fake runner nonzero blocked task T005 ▲ review NOT_READY — 6h T3 synthetic plan rejected to create blocked state

Pros

  • Strongest btop resemblance.
  • Fast scanning and stable mental model.
  • Easy to color by column and severity.

Cons

  • Per-store columns are still custom frontend decisions.
  • Needs responsive fallback when narrow.

Approach 2 — Universal columns across all stores

Most aligned with projection architecture Every store renders through the same columns: ID, Stage, Signal, Age, Priority, Summary. Store-specific detail goes into Signal and detail pane.

TASKS ID STAGE SIGNAL AGE PRI SUMMARY T002 ◆ plan no worktree 6h T3 synthetic active planning task T010 ▲ runner failed exit 42 6h T3 synthetic fake runner nonzero blocked task OBSERVATIONS ID STAGE SIGNAL AGE PRI SUMMARY L006 ◇ draft approve/revise 6h high synthetic architecture-risk contract draft L003 △ info needed answer info 6h norm synthetic observation needing info

Pros

  • Simple and consistent across stores.
  • Matches the future WatchProjection primitive.
  • New stores can render if they provide projection fields.

Cons

  • May be too generic for tasks; readiness/worktree info gets squeezed into Signal.
  • Less rich than Approach 1.

Approach 3 — Two-line rows: scan line + explanation line

Best for dense narrative data First line is table-like. Second line is optional and dim, carrying summary/detail. This reduces horizontal pressure.

ID STAGE SIGNAL AGE TIER T002 ◆ plan no worktree 6h T3 synthetic active planning task · next: plan review · not scaffolded T010 ▲ runner exit 42 6h T3 fake runner nonzero blocked task · log available in detail

Pros

  • Very readable on medium widths.
  • Summary stops fighting with status facts.
  • Can show more useful text without giant columns.

Cons

  • Half as many rows visible.
  • Feels less like btop and more like a log viewer.

Approach 4 — Density modes: compact table + detail inspector

Best long-term interaction model Default row is very compact; the right detail pane owns explanation. Toggle d or Tab for more row detail.

Compact TASKS ID STAGE SIGNAL AGE TIER T002 ◆ plan scaffold 6h T3 T003 ◇ review plan ◐ 6h T3 T010 ▲ runner exit 42 6h T3 Right detail for T010 State: runner failed · exit 42 Ready: — Why: fake runner nonzero blocked task Debug: blocked_reason JSON, logs, raw tuple

Pros

  • Maximum scan speed.
  • Right pane becomes the explanation surface.
  • Pairs well with keyboard navigation.

Cons

  • Requires users to trust the detail pane.
  • Some information disappears from the row by default.

Recommendation

Implement Approach 2 first, with Approach 1 as a per-store enrichment path.

  1. Make WatchProjection expose universal cells: id, stage, signal, age, priority, summary.
  2. Render focused rows through one table component with column headings.
  3. For tasks only, add an optional ready column if width allows.
  4. Keep raw readiness/debug facts in detail unless summarized into one Signal/Ready cell.
  5. Add color roles: heading bright, ID muted/magenta, stage severity-colored, age dim→warning if stale, priority color graded.

This gives the btop discipline without reintroducing a maze of store-specific prose renderers.
