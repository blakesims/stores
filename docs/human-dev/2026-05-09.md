## real good design

<pi-agent-design>
I think your instinct is right, and I’ll push back only on one phrase:

> “quite literally cloning btop”

The problem is not cloning btop’s **visual density / live dashboard / color grammar / process-table feel**. That is good.

The problem is cloning btop’s **resource model** too literally. CPU/memory are continuous scalar resources. Stores is not. Stores is a **typed flow network** with queues, gates, human approvals, retries, review loops, subscribers, and terminal sinks.

So the right analogy is not exactly “btop for tasks.” It is more like:

> **btop + factory flow monitor + circuit board debugger for the substrate.**

Or: **`flowtop`**.

## What I now think the core UI should be

You do **not** primarily want rows.

You want a **live graphical model of flow through the substrate**:

```text
INTAKE → OBSERVATION → CONTRACT → TASK → PLAN → EXECUTE → REVIEW → ACCEPT → INTEGRATE → SHIP
```

At each junction you want to see, visually:

- current queue depth
- inflow rate
- outflow rate
- age / latency
- blockage / failure rate
- retry/rejection pressure
- whether the bottleneck is AI, daemon, reviewer, runner, code, deploy, or Blake

That is much more ambitious — and much better — than “a better task list.”

## Pushback / stress test

The danger is building a beautiful dashboard that **pretends the engine has measurable flow** when the current substrate may not record enough event data cleanly enough.

To show rates like btop, we need real time-series-ish signals:

- transitions per minute/hour/day
- arrivals into intake/observations/tasks
- exits from each stage
- average/oldest age per queue
- rejection counts over rolling windows
- blocked counts by reason
- runner durations / failure rates
- subscriber lag / stale locks

Some of this exists in `transition_history`, timestamps, task logs, plan_review_log, cycles, external_reviews, dispatch_locks. Some may be derivable. Some may need instrumentation.

So the first implementation should be honest:

> use available event history to compute approximate rates now, then add better telemetry where the dashboard exposes blind spots.

That’s healthy dogfooding: the cockpit tells us what the substrate cannot yet see.

## Color grammar matters

You are right that text labels like `blocked` are not enough.

We need a visual grammar:

- **Green**: normal flow / recent throughput
- **Blue/cyan**: active running work
- **Yellow**: accumulating pressure / aging queue
- **Orange**: repeated retries/reviews
- **Red**: hard blockage / failed deploy / daemon dead
- **Purple**: human gate
- **Dim gray**: terminal/history/noise

And shapes:

- `▁▂▃▄▅▆▇█` for queue depth / rate
- `→` arrows colored by throughput
- `●` active work at a stage
- `◆` human gate
- `⚠` pressure
- `✖` failure
- `↻` retry/review loop
- tiny sparklines for rates over time

Do **not** start from Design A anymore.

1. Top: engine/runners health.
2. Main: graphical flow pipeline with rates, depths, age, and pressure.
3. Side/bottom: active process rows and failure badges.
4. Drilldown: selected stage or row expands into task list/logs/details.
